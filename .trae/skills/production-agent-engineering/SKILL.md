# Production Agent Engineering

把一个 agent 从 demo 推向生产时使用的工程方法论与检查清单。

## Core Principle
Agent 本质是后端服务，LLM 只是其中最显眼的组件。概念（prompt / context / harness / loop engineering）占 20%，工程占 80%。模型决定上限，工程决定下限。demo 写 happy path，生产处理 unhappy path。

## When to Invoke
- 将 agent 从 demo 推向生产
- 评审 agent 服务的可靠性 / 可观测性 / 成本
- 审计工具调用、状态管理、并发、记忆的实现
- 排查线上事故（卡死、重复调用、成本失控、无法定位）

## Agent 拆解 → 后端对应
| Agent 组件 | 后端对应 |
|---|---|
| LLM | 计算引擎（大脑） |
| 工具调用（跨网络） | 分布式 RPC |
| 短期记忆（上下文） | 内存管理 |
| 长期记忆（向量库 + RAG） | 数据库 + 检索引擎 |
| 编排 | 工作流引擎 |
| 多 agent 协作 | 分布式系统 |

## 七维生产就绪检查清单

### 1. 网络与工具调用（含 MCP，按 RPC 标准工程化）
工具调用（tool calling）是 LLM 的能力概念，其执行层只要跨网络就是 RPC——MCP（基于 JSON-RPC）、HTTP API、gRPC 都是 RPC 的具体实现。工具调用的发起者是 LLM 而非人，行为不确定，可能一轮调一次、下一轮调五次，必须按分布式 RPC 标准做。
- [ ] 认证：API key 不写死、不打日志、走密钥管理（Vault / 环境变量 / 配置中心）
- [ ] 超时：工具级 / 任务级 / 会话级三层超时，每层独立配置
- [ ] 重试：区分错误类型（4xx 不重试，5xx / 超时 / 网络错误重试），指数退避 + 抖动
- [ ] 幂等：所有有副作用的工具必须支持幂等键，重试不产生重复副作用
- [ ] 限流：客户端限流防被 ban，对下游服务做保护性限流
- [ ] 错误分类：可重试 / 不可重试 / 需降级，三类分别处理

### 2. 并发
- [ ] 流式输出异步化，禁止在 token 流上同步阻塞（如同步查库）
- [ ] 连接池合理配置，避免打满
- [ ] 多用户并发隔离，单用户故障不拖垮全局
- [ ] 异步 IO（事件循环 / 协程 / 线程池）按场景选型

### 3. 状态与上下文管理
- [ ] 上下文窗口策略：截断 / 压缩 / 摘要，明确「留什么、压什么、丢什么」
- [ ] 短期状态持久化，支持断点续跑与崩溃恢复
- [ ] 会话隔离，跨会话不串状态

### 4. 记忆与检索（长期状态）
- [ ] embedding 模型选型与评估
- [ ] chunk 切分策略（按语义 / 按长度 / 按结构）
- [ ] 索引建立与更新机制
- [ ] rerank 提升召回质量
- [ ] 召回质量离线评估集

### 5. 可靠性
- [ ] 熔断：连续失败达阈值熔断，避免雪崩
- [ ] 降级：工具不可用时返回兜底回复
- [ ] 死循环检测：最大步数限制 + 重复动作检测
- [ ] 人工接管通道：跑不下去时转人工
- [ ] 多 agent 协作的死锁 / 活锁防护（超时退出 + 最大轮次）
- [ ] 预算限制：单会话最大步数 / 最大 token / 最大成本上限，防 LLM 跑光额度

### 6. 可观测性
Agent 是巨大黑盒，一次请求可能调 LLM 三次、五个工具、两次向量库，没追踪出问题根本定位不了。
- [ ] 每步日志：输入、输出、耗时、token 数
- [ ] trace id 跨工具 / 跨 agent 串联
- [ ] metrics 面板：调用量、成功率、延迟分布（P50/P95/P99）
- [ ] token 消耗监控：按用户 / 按会话 / 按工具维度
- [ ] 成本告警：阈值触发报警

### 7. 评估
Agent 输出不确定，不能简单断言「输入 A 必输出 B」。
- [ ] 离线评估集
- [ ] 回归测试
- [ ] 在线 A/B 实验
- [ ] 人工 review 采样

## 常见线上事故模式（反面案例）
| 事故 | 根因 | 对应维度 |
|---|---|---|
| 重复扣款 / 重复下单 | 重试 + 非幂等 | 网络 |
| 服务卡死、用户多问几句就僵 | 同步阻塞 + 连接池打满 | 并发 |
| 月底账单失控 | 无成本监控 | 可观测 |
| 出问题无法定位 | 无 trace / 无日志 | 可观测 |
| CPU 拉满 | 无死循环检测 | 可靠性 |
| 上下文爆掉或质量下降 | 无窗口管理策略 | 状态与上下文 |
| 多 agent 互相发消息到死循环 | 活锁，无最大轮次 | 可靠性 |

## 推进路径（按优先级补齐）
1. **网络基础**：HTTP / RPC / 认证 / 超时 / 重试 / 幂等 —— 一切基础
2. **并发编程**：异步 / 协程 / 线程池 / 事件循环 —— 流式与多用户必备
3. **存储与缓存**：Redis / 关系库 / 向量库 —— 记忆与状态基础
4. **分布式系统**：消息队列 / 一致性 / 容错 / 编排 —— 多 agent 必备
5. **可观测性**：日志 / 追踪 / metrics —— 上线后靠它活
6. **评估体系**：离线评估集 / 回归测试 / 在线 A/B —— 上线后持续验证

## 使用方式
1. 拿一个 agent 项目，逐维过检查清单，标记 ✅ / ⚠️ / ❌
2. 对 ❌ 和 ⚠️ 项按「推进路径」优先级排修复顺序
3. 对照「常见事故模式」自查是否已存在同类风险
4. 评审新需求时，先问「这个工具调用幂等吗？」「这步有 trace 吗？」「成本谁监控？」
